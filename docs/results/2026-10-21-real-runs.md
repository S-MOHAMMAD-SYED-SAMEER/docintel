# The first real-model runs, 2026-10-21

**Read this first.** Every number below is from **synthetic documents with labels written by construction** (the values the documents were rendered from), **one run of each prompt, one model** (`claude-haiku-4-5`, which the API resolved to `claude-haiku-4-5-20251001`), on one day, at the model's default sampling (the adapter sets no temperature). They are a record of how this pipeline behaved on these documents; they are **not an accuracy figure, not a benchmark and not a claim about real invoices**. Sample sizes are small: 20 invoices (260 fields), a harder set of 10 (130 fields), and 3 purchase orders (30 fields).

Provenance of the labels: `invoices_v1` and `purchase_orders_smoke`: written by Claude (generated; the labels are the render inputs), no independent review. `invoices_hard_v1`: *Written by Claude (generated; labels are the render inputs); reviewed by ChatGPT and Claude; final decisions by Sameer.*

Raw records (every document, expected against extracted, per-field confidence and flag, the model's reply, tokens, cost, latency): the `2026-10-21-*.json` files in this folder. The plan and the decision rule these runs followed were committed before the first request: [`docs/EVAL.md`](../EVAL.md).

- **All of the improvement is on `invoices_v1`**, the set `invoice/v2` was written from (in-sample): 3 wrong fields became 0 (all three were `vendor_tax_id`). On `invoices_hard_v1`, the out-of-sample check, v1 and v2 each got 127 of 130 and missed the **same three fields** (below): no gain there. - The comparison was between two prompts on these documents. It says nothing about other documents or other models.

Per document, `claude-haiku-4-5`: about $0.0083 for a two-page text PDF (about 5,800 input and 450 to 510 output tokens), about $0.0069 for the hard set (several are single images), $0.0077 for the purchase orders; about 5.6 s a document (mean) on `invoices_v1`. ## What surprised me

1. **The same printed string was copied wrongly three different ways** (a dropped last digit, a dropped middle digit, a zero-width space), and correctly once, all reported at about the same confidence. The failures are random transcription errors, not a misreading of one layout.
2. **Two of those three were not flagged because the scorer's text-layer check passed them.** It matches a substring after dropping spaces and punctuation, so a truncated value and a value with an invisible character both count as "found". That is a defect in the scorer (found by this run, not fixed here on purpose so the v1/v2 comparison is not confounded); it is the next fix.
3. **On image documents the model's own confidence is the only signal** (there is no text layer), so a wrong value reported at 0.85 to 0.98 is not flagged (`hard-002`, `hard-008`). One of them sits exactly on the threshold: a final score of 0.850 is not below 0.85, so it passes.
4. **The deterministic checks earned their keep once**: `hard-003` has a date `04/03/2026` that could be April 3 or March 4; the model read it month-first under both prompts at 0.95 confidence, the due date `18/03/2026` made "due on or after invoice date" fail, and the field went to review. That is what the checks are for.
5. **The model "corrected" a spelling**: the page says `Munchen`, the model wrote `M\u00fcnchen` (both prompts), which the exact-match rule scores wrong. It is a plausible, helpful and wrong behaviour for an extraction task; the v2 paragraph covers identifiers only, not addresses.
6. **The hard set was not much harder for this model**: 127 of 130 against 257 of 260 on the easy set, and the three misses on each are not the failures the set was designed around (the stamp, the photograph, the credit note, the missing due date and the two-page table were all read correctly). Difficulty was set by hand, not measured; ten documents cannot say more.
7. **The two scoring rules decided before the runs changed no result**: the credit note (`hard-004`) was extracted exactly as labelled (negative quantities, positive unit prices) under both prompts, so the either-sign rule was not needed, and `hard-009`'s missing due date was reported as null under both.

## Limits

- Synthetic documents from a small invented pool; labels by construction; the hard set was reviewed by an AI and a person, not independently annotated.
- One run of each prompt at default sampling: no estimate of run-to-run variation exists, and the failure being studied was variable.
- One model. No other model, no other provider, no real invoice, no handwriting, no other languages beyond two European formats.
- 20, 10 and 3 documents: a miss or a hit moves a rate by 0.4 to 3 points.
- The confidence weights and the threshold are untuned defaults; the false-confident counts (4 and 2 of 390 fields) are too small to say how well the weighting works.
- Cost figures come from token counts and a hand-entered price list.
